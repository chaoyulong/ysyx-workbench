# 性能记录表（Performance Records）

每次性能优化后执行 `make perf` 记录结果，配合 `git checkout <commit>` 可复现当时代码的性能数据。

## 使用方法

```bash
make perf                    # 运行 microbench(test 规模), 输出: 仿真周期数/指令数/IPC + PERF 计数器
make sta                     # 综合(nangate45), 频率/面积见 build/sta/ysyx_23060082-500MHz/
make sta STA_PDK=icsprout55  # 换流片工艺综合
```

- **仿真周期数 / 指令数 / IPC**：`make perf` 输出中的 `total execution cycle / inst / instructions per cycle`
- **综合频率 / 面积**：`make sta` 后查看 `build/sta/ysyx_23060082-500MHz/`（时序报告给出可达频率，`synth_stat.txt` 给出 `Chip area`）
- **真实时间(ms)**：`仿真周期数 ÷ 综合频率` —— 把"周期"和"频率"两个方向的优化合成一个总账（**注意它按 STA 报告的可达频率换算，是同工艺内才可比的量**）
- **PERF 计数器**：`make perf` 输出的 `============ PERF ============` 表格（IFU/LSU 延迟、EXU 计算周期、指令类别占比）

## 记录步骤

1. `git log --oneline` 确认当前 commit
2. 执行 `make perf`，从输出抄录周期数/指令数/IPC 和 PERF 表格
3. 执行 `make sta`，从报告抄录综合频率/面积
4. 将数据填入上表（commit + 说明 + 数据），提交 `PERF.md`

## 说明

- **commit 列为 `(实验)` 的行**：表示**未提交**的实验状态（只在 PERF.md 里存档，无法用 `git checkout` 复现）。例如"把 3 个无用信号加回去"那一行 —— 它的 RTL **逻辑**与相邻的 `103146f` **完全相同**（周期/指令数逐位相同），存在的意义只是量化"**语义中性的扰动会让 ABC 换一套映射、从而改变面积与频率**"这件事。
- **工艺**：`综合面积` **只在同一工艺内可比**（各行在"说明"列注明工艺）。教程的面积限制按 **nangate45** 判定；`make sta STA_PDK=icsprout55` 可切回 icsprout55 流片工艺，同一份 RTL 两者相差约 30%
- **真实时间(ms)**：`仿真周期数 ÷ 综合频率(MHz)`，单位 ms。用途是**把"降周期"和"提频率"两类优化放在同一个尺子上**（例如 `d1cdfe4→92a825d` 是周期 +0.78%、频率 +12%，净结果 15.25ms → 13.91ms，赚 8.8%）。
  两个注意：① 它同样**只在同一工艺内可比**（频率随工艺变，`[icsprout55]` 行不能和 `[nangate45]` 行直接比）；② 它按 STA 的**可达频率**换算，不是"评分口径"——评分只要求 500MHz 通过，若按 500MHz 算则是 `周期数 × 2ns`，那一列与周期数完全同序，所以这里不单列。
- **取指总周期**：所有取指请求累计周期数（= 取指avg × 取指次数）
- **取指avg**：PerfReg 延迟组 0 的平均值。**注意**：命中是"请求即响应"(同拍)，而 PerfReg 在同拍 req+rsp 时读到的是**上一次**请求的时间戳，故该值实际接近"两次取指的平均间隔"，不是纯取指延迟
- **取指命中率 / 缺失avg**：icache 的 `io.miss`、`io.missDone` 两个脉冲统计而来；`缺失avg` 即**平均缺失代价**，也就是文档 TMT（总缺失时间 = 缺失次数 × 缺失代价）里的那一项
- **LSU访存总周期**：内存读+写累计周期数（= rd total + wr total）
- **LSU mem rd/wr avg**：内存读/写平均延迟（cyc/access）
- **LSU dev avg**：外设访问平均延迟（串口/键盘/CLINT/VGA 等）
- **EXU calc**：计算类指令总执行周期（当前单周期，= 计算类指令数）
- **calc/mem/branch/jump/csr/sys%**：指令类别占比（decoder 统计）
- 不同 commit 的计数器含义可能不同（如早期无 PerfReg、604d59c 起才有命中率），以当时代码输出为准

### 519cf4f(五级流水线) 起的两点注意

- **指令类别百分比**：`519cf4f` 那行的类别计数还是按 `io.input.valid` 计的（属于该级的**占用拍数**，不是指令条数，百分比相对"各类别之和"算）；**从 `bbd3432` 起已改成按 `io.output.fire` 计数，恢复"指令条数占比"语义**（`Σ类别` ≈ 658280，比退休指令数略大，因为被重定向冲掉、但已经离开 IDU 的指令也计了一次）。
- **本版瓶颈不在流水线**：LSU 访存（rd 7.74M + wr 1.21M）+ icache 缺失（3.85M）≈ 12.80M / 13.71M = **93.4% 的周期在等访存**，所以 5 级流水线只比多周期版少 5.7% 周期（`bbd3432` 再降 4.5% 也只是把协议白等砍掉）。
- **取指次数 817065 vs 退休指令 581595**：约 29% 的取指被丢弃（重定向冲刷 + 提前取指），并且把 icache 缺失次数从 47.5K 顶到 70.9K（+49%）——错路径取指会真实地吃 miss 代价。
- 综合频率 `bbd3432` = 587.8 MHz（500MHz 目标下最差路径 slack 0.299ns，路径仍在 `ifu.icache.axi4Ctrler.io_readAddr`）。

### 92a825d 的取舍：拿 0.78% 周期换 12% 频率

- **做对了什么**：icache 的 `ar.valid/addr` 恢复成寄存器后，交给 Xbar 的是**寄存器信号**，一次切断了「icache 的 hit 锥 → Xbar 地址 mux / `isClint` 解码 → CLINT 的 `ar.fire` → `readCnt/readActive/dataFinish`」整族长组合锥 → 榜首从 CLINT 的 `readCnt`（1.085ns，其实是一条**不可敏化**的假路径：IFU 的取指地址永远不会落在 CLINT 的 `0x0200_0000` 段）换成真正的核内路径。
- **代价比预估略大**：每次 icache miss 的 AR 晚 1 拍（预期 +0.52%），实测 **+0.78%** —— 因为 AR 晚一拍也更容易在 Xbar 上把总线让给 LSU，`缺失avg` 从 54.31 涨到 **59.69 cyc/miss**；这部分常被流水线停顿吸收，所以总周期增幅（+0.78%）小于「miss 次数 × 5.4 拍」。
- **换来了什么**：频率 888 → **993.6 MHz**（+12%），面积 −232.5 µm²，而且**第一次看到了真实瓶颈** —— 不再是 cache/CLINT，而是
  - `exu.io_input_payload_rfReadData{1,2}_*`：IDU 的 **RF 读 + 三级前递 mux** → IDU→EXU 寄存器（0.951~0.957ns）
  - `ifu.state_0`：IFU 的次态逻辑（重定向 / 响应 / Done 的 mux，0.964ns）
- **判断**：如果只看周期，这 +0.78% 是净亏；但用新增的"真实时间"列算总账，`d1cdfe4` 的 15.25ms → `92a825d` 的 **13.91ms（赚 8.8%）** —— 频率涨得比周期亏得多。评分口径是周期 + 面积、频率只要求"500MHz 通过"，所以这 0.78% 周期在评分上仍是净亏；保留它的理由是频率余量（994MHz ≈ 2 倍）和"把假路径从报告里清掉、让真瓶颈暴露"。若只在乎评分，可以只回退 icache 那一处（CLINT 的寄存器化与计数器拆分应当保留）。

### c252c6c 的取舍：同步复位要花掉 0.36ns 关键路径（面积反而更小）

项目要求同步复位，改法只有一行（`Config.scala`）：

```scala
defaultConfigForClockDomains = ClockDomainConfig(
  resetKind = SYNC,            // SpinalHDL 默认是 ASYNC
  resetActiveLevel = HIGH)
```

- **验证方式（两个层面）**：生成 RTL 里 `or posedge reset` 从有到 **0 处**；网表里 `DFFR_X1`(579 个) + `DFFS_X1`(9 个) **全部消失**，只剩 `DFF_X1`(3036 个)。
- **功能验证**：`make perf` 的周期/指令数/全部 PERF 计数器与 `92a825d` **逐位相同** ✓ —— 复位只在上电生效，行为零变化。
- **对照实验**（只把 `resetKind` 改回 `ASYNC`，其他一个字不动）：

| 配置 | 面积 | 最差路径 | 频率 | 500MHz slack |
|---|---|---|---|---|
| `92a825d`（ASYNC，未清理复位）| 22,364.75 | 0.964ns | 993.6 MHz | +0.994ns |
| **c252c6c（SYNC + 清理）** | **22,478.33** | **1.387ns** | **698.6 MHz** | **+0.569ns ✓ 达标** |
| 对照（ASYNC + 同样的清理）| 22,625.43 | 1.029ns | 929.2 MHz | +0.924ns |

- **两条重要结论**：
  1. **同步复位的代价是"关键路径 +0.36ns"，而面积反而更小（−147 µm²）** —— 因为复位变成了"参与数据路径的高扇出信号"，每个带复位触发器 D 侧多一层 mux、复位还要像普通信号一样满足建立时间；而异步复位用专用复位脚、不需要 D 侧逻辑。**面积与关键路径是两本独立的账，减少线不保证缩短路径。**
  2. 同步复位**把一条本来不是最长的路径顶成了最长**：ASYNC 版榜首是 `ifu.rdataReg_31`（1.029ns），SYNC 版榜首变成 EXU 的 imm/branch/pcNext 锥（1.387ns）。
- **去掉可省的复位**（按"上电后可能被读而此前从未被写"的规则）：icache 的 `lineReg`(128b)/`wordCnt`/`wordSelReg`/`pcReg`/`indexReg`/`tagReg`、IFU 的 `pcOfReq`、LSU 的 `rdataReg`、CLINT 的 `readLen`/`readCnt`/`timeCountHighSnap`；**必须保留**的是各状态机、流水线 valid、AXI 握手 valid、icache 行有效位、CSR 的 `mstatus/mtvec/mcause`、CLINT 的 `timeCountLow/High`（项目要求初始为 0）。这一轮清理把同步复位的面积代价从 **+502 µm² 压到 +114 µm²**（相对 `92a825d`）。
- **注意**：报告里的"可达频率"会随"复位种类 + 再映射"大幅跳动（这一路走过 587→739→898→993→799→698 MHz，而期间周期数几乎没变），**判断标准应看 500MHz 目标下的 slack 是否为正**，不要只看这个数。

### f9d00c5：一个取指闸门吃到两份收益（周期 −6.1%）

- **思路**：`jal`/`jalr` **必然重定向**，所以它们之后顺序取的指令 **100% 会被丢弃**；而这些错路径取指**既自己缺失、又污染 cache**。于是在 IFU 里对"刚取到的指令"预译码（只看 opcode：jal=`1101111` / jalr=`1100111`），一发现就把取指闸门关上，直到重定向重启前端。
- **实测**：周期 13,822,167 → **12,975,343（−6.13%）**、IPC 0.0421 → **0.0448**、Scored time 6058 → **5203 ms**；IFU 取指 797,102 → **769,871（−3.4%）**、icache 缺失 70,893 → **52,810（−25.5%）**、命中率 91.11% → **93.14%**；**LSU 读写完全不变**（没碰访存）；面积 22,478.33 → **22,460.24**、500MHz slack +0.569 → **+0.711ns**。三个指标全赢。
- **为什么缺失降得比取指降得多**：减少的取指 27,231 次里有 **66%（18,083）会 miss** —— 错路径取指既自己缺失，又挤掉有用的行，所以一个闸门吃到两份收益。（原先估"错路径里只有 8% 会 miss"是错的。）
- **★ 死锁坑（第一版）**：置位条件必须用 `io.output.valid` 限定！`icache.io.rspOut.valid = (reqIn.fire && hit) || missDone`，其中 `missDone` **会迟到**：若重定向发生在缺失填充期间，填充完成时 IFU 已回到 Idle、等的是新 pc，这条"已作废"的响应仍会拉高 `rspOut.valid`。只看 `rspOut.valid && isJump` 时，一条废弃路径上的 jalr 就会把 `stopFetch` **永久置起**（它只被 redirect 清）→ 前端从此不再取指 → 死锁（表现为 `一条指令超过10000周期未完成 (pc=0xa0005668)`，那条正是 `ret` = jalr）。`io.output.valid` 里 missDone 那一项要求 `state===WaitMem`，正好排除这种迟到响应。
- **剩余空间**：现在 52,810 次缺失 vs 按退休 PC 算的理想值 47,610 → **多余的只剩约 5,200 次（10%）**，所以"把闸门扩展到条件分支"的收益已不大（约 2%）；下一刀应转向**顺序预取**（fetch 侧）或 sectored dcache（load 侧）。

### 1d85319：D-Cache 的取舍（周期 −2.82%，但面积只剩 169 µm²）

- **结构**：4 项 × 1 个字（4B）直接映射，**写穿 + 写不分配**；dcache 内复用 `Axi4_Ctrler` 并**独占 CPU 的 AXI 口** → 不需要第二个控制器、不需要任何 AXI 通道 mux。只缓存 flash 与 PSRAM/SDRAM（trace 实测 flash 阶段数据命中率 **0.00%**，纯流式零复用，缓存它只有成本没有收益）。store 命中时**同步更新 cache 里那一个字**（这是"只读 cache"唯一的正确性要点，否则之后 load 会读到旧值）。
- **实测**：周期 12,975,343 → **12,609,428（−2.82%）**、IPC 0.0448 → **0.0462**；LSU 读事务 75,728 → **64,258**（`Dcache access` 命中率 **15.15%**，与 cachesim 预测的 4×4B = 16.89% 吻合）；icache 缺失 avg **60.83 不变**（无争用）；面积 22,460.24 → **24,830.83**；500MHz slack **+0.799ns**；两个平台 shuixianhua 与 microbench 均 PASS。
- **教训一：缺失开销必须为 0，命中率才换得到周期。** 此前两版都亏 —— 整行 8B 填充（每次缺失多花 ~34 拍 → 净 **+0.52%**）、icache 顺序预取（多出来的事务被争用吃掉 → 净 **+3.8%**）。本版每次缺失就是**一次单字读**，与基线开销完全相同，于是每一次命中都是纯赚。
- **教训二：两个握手坑（都踩过，症状都是"错数据"）。**
  1. **不能用 `rspOut.valid` 判"读命中"** —— 它还包含上一笔 store 的 `b` 响应和上一笔缺失的完成 → 一次 load 会拿别人的响应"当拍完成"、拿到旧数据 → ALU/分支结果错乱 → **死循环**。必须由 dcache 导出真正的 `readHit`。
  2. **`Idle → WaitMem` 必须等 `reqIn.fire`** —— 否则 dcache 忙（还在 `Write`）时这次请求被丢掉，LSU 只能等到一个属于别人的响应。
- **注意**：本版面积余量只剩 **169 µm²**（再映射抖动本身就有 ±250）→ 后续要加东西（例如 store buffer）必须**先腾面积**。

### f1b8c26：异常处理（**周期零成本**）

- **统一异常通道**：payload 的 `CsrCtrl` 里带两个字段 —— `trapEnter`（"有异常要进"，各阶段都能置）与 `excCause`（4 位异常号）。
  每级的合并规则统一写成"**上游优先**"：`trapEnter := 上游.trapEnter || 本级异常`，`excCause := Mux(上游.trapEnter, 上游.excCause, 本级cause)`
  → 更老的指令先到生效点、并且会覆盖更年轻的 → **"最老的异常胜出"自动成立**（正是"多异常同时发生"要求的语义）。
- **各级产生**：

  | 部件 | 异常号 | 说明 |
  |---|---|---|
  | IFU | 0 / 1 / 12 | 0=取指地址未对齐(兜底)｜1=总线读回非 OKAY（icache 新增 `rspErr`，且**错误行不写进 cache**）｜12=页错误（MMU 接口先接 0）|
  | IDU(Decoder) | 2 / 3 / ecall | 非法指令、ebreak、ecall；`i_illegal` 已改为 `!isLegal`（原先的 `instr =/= 0` 豁免会让"全 0 指令"静默执行）|
  | EXU | 0 | 跳转/分支**目标**未对齐（`pcNext(1)`）；同时**抑制自己的重定向**，否则会真的跳到非对齐地址并与 trap 的重定向打架 |
  | LSU | 4 / 5 / 6 / 7 | 4/6=访存地址未对齐（**必须在发请求之前判定**）｜5/7=总线读/写错误（dcache 新导出 `readErr`/`writeErr`）|

- **生效点（LSU）**：`mepc := io.input.pc`（**出错指令自己的 pc**，随指令一路传下来 → 精确异常）、`mcause := Mux(ecall, a5, excCause)`、`mstatus` 的 MIE/MPIE/MPP、重定向到 `mtvec`；同时**抑制该指令的副作用**：不访存（`reqIn.valid && !trapEnter`）、不写回（`regWr && !trapEnter`）、不执行自己的 CSR 写（`csrCmd := 0`）。`trapExit`(mret) 单独一路：不写 mepc/mcause，只恢复 `mstatus` 并跳回 `mepc`。
- **ecall 的 cause 走 a5（AM 约定，勿改）**：`__am_irq_handle` 把 `mcause` 当"事件号"用（`yield()` 是 `li a5,-1; ecall`），所以不能按规范改成固定 11；因此 `causeIn := Mux(ecall, io.input.rfReadData, excCause.resize(32))` —— ecall 必须取**完整 32 位**，否则 `-1` 就错了。
- **实测**：周期 **12,309,885 与上一版逐位相同** → 异常机制在**无异常路径上零成本**；面积 24,774.44 → **24,701.03**（余量 298.97）；500MHz slack **+0.989ns**；microbench 与 shuixianhua(npc+ysyxsoc) 全 PASS。
- **已隐式验证**：cpu-tests 每次 `printf`/`putch` 都是 ecall → trap → handler → mret，等于把"trap 进入 / mepc·mcause 写入 / mstatus 更新 / mret 返回 / 重定向与前端 flush"这条完整回路跑了几万次。
- **尚待专门验证**：故障类（0/4/5/6/7/12）现有测试不触发，需要自建用例（`.word 0xdeadbeef`、内联汇编造未对齐 lw/sw、ebreak）或在仿真里强制 `rspErr`/`pfFault`。

### 103146f：difftest 接入（**周期零成本**）+ "无用信号 → ABC 映射"实验

#### difftest：与 NEMU 逐指令对拍

移植 NEMU 的 `src/cpu/difftest/dut.c` 与 `include/cpu/difftest.h`（`csrc/difftest.c` / `include/difftest.h`），有 5 处**必须适配**：

| # | NEMU 的写法 | 本工程为什么不能照抄 | 改法 |
|---|---|---|---|
| 1 | `checkregs` 比 `cpu.pc` | NEMU 调用时 `cpu.pc` 已是**执行后**的 pc；本工程的 `cpu.base.pc` 是**本条**指令的 pc | 比 `cpu.pcNext`（`itraceRetirePcNext`）—— 用 `cpu.base.pc` 会"每条都 diff" |
| 2 | skip 回灌 `&cpu` | 回灌的 pc 若用 `cpu.base.pc`，ref 会退回本条重跑 → 之后全线 diff | 用 `pc = pcNext` 的副本回灌 |
| 3 | `guest_to_host(RESET_VECTOR)` | `CONFIG_MBASE` 恒为 0x8000_0000，而 ysyxsoc 的 `RESET_VECTOR` = 0x3000_0000 → **指针下溢** | 直接用 `flash[]` 数组首址（两平台都对）|
| 4 | 没传 `-d` 就 `assert` | 会把 `make perf` 带崩 | 视为"关闭 difftest"并打一条警告 |
| 5 | `skip_dut`（QEMU 指令打包追赶）| ref 是 NEMU 解释器，`exec(1)` 恒等于一条指令 | 删掉 |

- **接口契约**：`cpu_base_state_t = {gpr[32], pc}` = **132 字节**（与 NEMU `CONFIG_RVE` 关闭时的 `riscv32_CPU_state` 一致，也是 `difftest_regcpy` 的 `sizeof`）。编译期 `static_assert(sizeof==132 && offsetof(pc)==128)`；启动时再跑 `difftest_abi_check()`（给 ref 一个 256 字节缓冲区、用 0xCC 哨兵量它到底写多少字节）→ **NEMU 那边一旦打开 `CONFIG_RVE`（变 68 字节）会当场报错，而不是静默错位**。
- **ref 跳过判据 `difftestSkip`（在 LSU 合成 1 bit，经 `Lsu2Wbu_data → WBU → ItraceReg` 给 C 侧）**：`trapEnter | mret | CSR 指令 | fence.i | 设备访存`。三类必须跳过的原因：设备访存在 ref 里不存在（`out_of_bound` → panic）；ref 只实现 4 个 CSR，而 `_trm_init → ysyxsoc_dis_id()` **每条程序开头**都读 `mvendorid/marchid`；ecall 的 mcause 约定不同（dut 走 a5，NEMU 走 a7）。
  ⚠ **被跳过的指令只能没有内存副作用**（回灌只同步 `{gpr, pc}`，不同步内存）→ 设备判据必须与 NEMU 的 `in_mem_region` 一致，**SRAM 要算内存**（ysyxsoc 的 ssbl 在 SRAM 里执行、拿 SRAM 当栈），**不能复用 perf/mtrace 那个把 SRAM 当设备的 `isDevAddr`**。整段在 `if (enableSimDebug)` 内 → `make sta` 一行都不生成（零面积）。
- **实测**：同一份镜像、同一份 RTL，**带 / 不带 `-d` 的周期与指令数逐位相同（12,235,206 / 555,737）** → difftest 对 DUT 完全透明，只影响宿主墙钟时间（不带 `-d` 14.2s，带 difftest 会慢很多倍）。面积 24,457.64 vs `f1b8c26` 的 24,701.03（差 243 µm²，在 ±100~250 抖动内）。

#### 与 `f1b8c26` 不可直接比

本行的树同时含"平台配置拆分（`PARTFORM` / npc 复位 0x8000_0000）+ 退休 pc 下一条（仿真专用）+ difftest + 删无用信号"。指令数 582,020 → 555,737（**−4.5%**）而周期只 **−0.6%** —— 差额来自 ysyxsoc 的**引导装载**与**设备轮询**这类"时序/镜像敏感"路径，**与 difftest 无关**：

- `_second_stage_bootloader` 按 **4 字节/次**循环搬镜像，反汇编实测循环体**正好 6 条指令** → **≈1.5 条指令/字节镜像**；当前镜像 31,208 字节 → 约 **4.7 万条指令（占 8.4%）**。
- 每次 `putch` 都要 `while(!(UART->LSR & 0x20));`（本行 `LSU dev rd cnt = 712`、总 3,422 周期）。

#### "无用信号 → ABC 映射"实验（**结论：不保留**）

`readHigh`(CLINT) / `normalPc`(IFU) / `writeDone`(dcache) 三个**无人读**的信号：

| 变体 | 面积 (µm²) | slack | 频率 | 最差路径 | 生成 RTL md5 |
|---|---|---|---|---|---|
| 带这 3 个信号 | 24981.39 | +1.008 | **1007.65 MHz** | `ifu.icache.axi4Ctrler.io_readAddr_30__reg_p:D` | `ecdde12522` |
| **删掉（本行）** | **24457.64** | **+0.920** | **925.66 MHz** | `lsu.csr.minstreth_23__reg_p:D` | `e43a3480d5` |
| 删掉 + **另外 3 个完全无关**的无用信号 | 24803.44 | +0.986 | **986.23 MHz** | `ifu.icache.axi4Ctrler.io_readAddr_30__reg_p:D` | `7faf4fa66d` |

- **每行各跑 2 次，area / slack / freq / 最差路径 / RTL md5 全部逐位相同** → 同一份源码的 STA 结果是**确定的**；但换源码（哪怕只增删一个无害信号）就会**重新抽一次签**。
- **换成完全无关的无用信号同样得到 986 MHz** → 起作用的是"给 ABC 的输入网表加一点语义中性扰动"，**与具体是哪几个信号无关**（ABC 的 `resyn2/choice/map` 是全局启发式，输入节点顺序一变，面积/关键路径/频率整体换一套）。
- 也正因如此：**面积差 524 µm² 不是那几个门本身的面积**，而是映射被整体改变的结果 —— 这也解释了为什么"删掉三个死信号"会同时掉 524 µm² 面积与 82 MHz 频率。
- **删掉的理由**：① 收益是"抽签式"的、不可预测，也可能变差；② 带信号时面积距 25,000 硬上限只剩 **18.6 µm²**（删掉后有 **542.4 µm²**）；③ 评分口径是 **周期 + 面积**，频率只要求 500MHz 通过（925 MHz 已是 1.85 倍余量）；三者的**周期与指令数逐位相同**。
- ⚠ 想"提频"应该去动真瓶颈（当前最差路径 = IFU 的 pc 选择 mux → icache `ar.addr` 寄存器），而不是靠无用信号扰动映射。

### f6ceec4：mcycle/minstret 进位"寄存一拍" —— 频率 +3.2%，周期零变化

**动机**：基线（`103146f`）STA 的**最差 5 条端点全是同一个东西** ✗ —— `lsu.csr.minstreth_23/24/25/30/31__reg_p:D`（slack 0.920~0.928 ns，彼此只差 0.008 ns ✓）。

**根因**（看 D 输入上的单元链就能读出来）：
```
[低 32 位加法器进位链] → [低位 == 0xffffffff 的 32 输入比较] → [高位 32 位加法器进位链]
        ≈32 级                       ≈2~3 级                        ≈24~31 级
```
⇒ **一个周期里要串完 ~55~65 级逻辑** ✗（nangate45 + X1 单元下，32 位行波进位加法器本身就要 ~0.6 ns ✗）。原写法虽然已经拆成了低/高两个 32 位寄存器 ✓，但"低位溢出"这个进位是**组合传上去的** ✗，等于没拆断 ✓。

**改法**（`playground/src/CSR.scala`，4 行 + 2 个触发器）：
```scala
mcycle := mcycle + 1
when(writeEnable && io.csrCmd === 1 && (io.csrAddr === CSR.mcycle || io.csrAddr === CSR.mcycleh)) {
  mcycleCarry := False                        // 软件写入为准: 清掉挂起的进位
} elsewhen(mcycle === U"32'hffffffff") {
  mcycleCarry := True                         // ★ 低位即将溢出 -> 进位寄存一拍
} otherwise {
  mcycleCarry := False
}
when(mcycleCarry) { mcycleh := mcycleh + 1 }  // 高位只由【进位寄存器 Q】驱动
```
（`minstret` 同理 ✓；进位是拿**寄存器自己的 Q** 去比较 `0xffffffff` 得到的 ✓，所以进位触发器的 D 路径只有约 4~5 级 ✓，**完全不含加法器** ✓）

### 1a8a3e2：dcache 读写解耦（"写穿不等 b"）+ CLINT 单拍读 + 去掉进位打拍 —— 周期 −2.67%

**动机**：基线 `103146f` 的周期构成里 **LSU 访存占 60.5%** ✗（7,399,562 cyc，115.81 cyc/次读），而其中**总线本身只占 ~29 cyc** ✓（把 icache 的单拍缺失折算过来是 28.9 cyc ✓）—— 剩下 ~87 cyc 全是**端口串行化** ✗。

**根因**：dcache 里一次 store 要**独占**着走完 `aw/w → b` 整个往返（~20 拍）才回 `Idle` ✗，而 `reqIn.ready = (state === Idle)` ⇒ 这 ~20 拍里**下一笔访存（哪怕只是个读）一律进不来** ✗。但读和写在 AXI 上本来就是两个独立通道 ✓（Xbar 早就解耦了 ✓）⇒ 串行化完全发生在 dcache 自己这里 ✗。

**改法**（`playground/src/dcache.scala`）—— 核心一句话：**"某个事务正在飞"这件事不能用 FSM 状态来表达** ✗

1. **写出即松手**：可缓存写的 `aw/w` 都发出去后（`writeSent = !aw.valid && !w.valid` ✓）立刻回 `Idle` ✓；`b` 交给 **`bPending`** 寄存器在后台等 ✓
2. **设备/MMIO 写不吃这套** ✗：`writePostDone` 要求 `writeCacheable` ✓ ⇒ 设备写仍严格等 `b` ✓ ⇒ **MMIO 读写顺序一点没动** ✓
3. **顺序性 guard**：`bPending` 期间，**新写** ✓ 与**同字（`addr[31:2]`）且未命中**的读 ✗ 都必须等 `b`（否则读可能先到内存、拿到旧值 ✗）
   - **命中读永远放行** ✓：写穿 + 写不分配 ⇒ 若那笔写命中，cache 里已是新值 ✓；若没命中，那个字根本不在 cache 里 ⇒ 读它必然是缺失 ✗ ⇒ **"命中读"绝不可能读到受挂起写影响的数据** ✓（这条豁免很值钱 ✓：命中读占绝大多数 ✓）
4. `writeBusy := (state === Write) || bPending` ✓ ⇒ `fence.i` 等到的仍是"写真正落地" ✓
5. **读路径一行没改** ✓：FSM 现在**只跟踪读**（`Idle → ReadMiss → Idle` ✓），所以 `readHit` / `readMissDone` 保持原来"按状态解码"的写法 ✓ ⇒ "读响应被丢"这类死锁在结构上不存在 ✓

**★ 最大的坑：五处口径必须完全一致** ✗

- **`CLINT.scala`：读通道去掉突发支持（只做单拍读）** ✓ —— 本设计里安全 ✓（只有 icache 会发 4 拍突发 ✓，而**取指永远不落在 CLINT 段** ✓；LSU/dcache 全是单拍 ✓）：删掉 `readLen`/`readCnt` ✓、`r.last := True` ✓（省掉一个计数器 + 8 位比较 ✓）。

### 6a6d85d：iverilog 网表的 X 根因（CSR 侧控制信号未按 valid 门控）

- **现象**：RTL 四值 microbench 全过，但网表跑到 cyc≈42261 顶层 `io_master_arvalid` 先变 X，随后 `araddr`/`aw`/`w` 全 X；网表比 RTL 慢几十倍（4M 拍只到 `[qsort]`、UART 98B vs RTL 124B）。
- **定位**（VCD 窗口 + 寄存器 Q 级追踪）：
  1. 网表在**复位释放那一拍**（cyc 50）把 `lsu.csr` 的 `mtvec/mstatus/mcause/mcycle/minstret` 全部写成 X —— RTL 里 `if(reset) q<=0` 是程序分支、`if(X)` 被当假分支吃掉；综合成门后复位只是 D 端 mux 的一项，控制信号 X 会直接写进寄存器。
  2. 这些 X 经前递/比较传到 `exu.redirect.valid`，再经 IFU 的"重定向/顺序"mux 写进 `pcFetch`（cyc 42253 第一个变 X 的控制寄存器），随后 icache 地址 X → Xbar 地址解码 X → 顶层 `arvalid/araddr` X（cyc 42260）。Xbar 的 `readState/arbiterState` 只是**最后被污染**的（D 端先 X、Q 后一拍 X）⇒ "状态机漏复位"的假设不成立。
- **修复**（`LSU.scala`，零新增触发器）：CSR 侧三条控制信号一律与已复位的 `io.input.valid` 相与 —— `csrCmd = Mux(trapEnter || !valid, 0, ...)`、`trapEnter = valid && trapEnter`、`trapExit = valid && trapExit`。
- **验收**：网表 X 消失（端口含 X 周期 787→47，且只剩启动瞬态、无有效事务上的 X）；网表全量 microbench 10/10 PASS、UART 539B、AXI `ar/aw/rbeat/wbeat = 104590/48668/252778/48668` 与 RTL 逐位一致；rtthread（新 bin）网表跑到 RTT 自动 microbench PASS 后按"UART 出现 `AM Panic:`"收尾；`make perf` / `make sta` 见上表行。
- **残留（协议内正常，刻意不动）**：`mepc`、`regFile.rf_3/rf_4`、`clint.wStrbFullReg` 在窗口起点仍是 X —— 它们只会在"先写后读"的协议保证下被选中，不会逃逸到控制路径；给它们加复位要 32/512 个触发器，远超 9 µm² 的面积余量。
