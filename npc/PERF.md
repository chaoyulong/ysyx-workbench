# 性能记录表（Performance Records）

每次性能优化后执行 `make perf` 记录结果，配合 `git checkout <commit>` 可复现当时代码的性能数据。

## 使用方法

```bash
make perf                    # 运行 microbench(test 规模), 输出: 仿真周期数/指令数/IPC + PERF 计数器
make sta                     # 综合(nangate45), 频率/面积见 build/sta/ysyx_23060082-500MHz/
make sta STA_PDK=icsprout55  # 换流片工艺综合
```

- **仿真周期数 / 指令数 / IPC**：`make perf` 输出中的 `total execution cycle / inst / instructions per cycle`
- **综合频率 / 面积**：`make sta` 后查看 `build/sta/ysyx_23060082-500MHz/`（时序报告给出可达频率，`synth_stat.txt` 给出 `Chip area`）
- **真实时间(ms)**：`仿真周期数 ÷ 综合频率` —— 把"周期"和"频率"两个方向的优化合成一个总账（**注意它按 STA 报告的可达频率换算，是同工艺内才可比的量**）
- **PERF 计数器**：`make perf` 输出的 `============ PERF ============` 表格（IFU/LSU 延迟、EXU 计算周期、指令类别占比）

## 记录步骤

1. `git log --oneline` 确认当前 commit
2. 执行 `make perf`，从输出抄录周期数/指令数/IPC 和 PERF 表格
3. 执行 `make sta`，从报告抄录综合频率/面积
4. 将数据填入上表（commit + 说明 + 数据），提交 `PERF.md`

## 说明

- **工艺**：`综合面积` **只在同一工艺内可比**（各行在"说明"列注明工艺）。教程的面积限制按 **nangate45** 判定；`make sta STA_PDK=icsprout55` 可切回 icsprout55 流片工艺，同一份 RTL 两者相差约 30%
- **真实时间(ms)**：`仿真周期数 ÷ 综合频率(MHz)`，单位 ms。用途是**把"降周期"和"提频率"两类优化放在同一个尺子上**（例如 `d1cdfe4→92a825d` 是周期 +0.78%、频率 +12%，净结果 15.25ms → 13.91ms，赚 8.8%）。
  两个注意：① 它同样**只在同一工艺内可比**（频率随工艺变，`[icsprout55]` 行不能和 `[nangate45]` 行直接比）；② 它按 STA 的**可达频率**换算，不是"评分口径"——评分只要求 500MHz 通过，若按 500MHz 算则是 `周期数 × 2ns`，那一列与周期数完全同序，所以这里不单列。
- **取指总周期**：所有取指请求累计周期数（= 取指avg × 取指次数）
- **取指avg**：PerfReg 延迟组 0 的平均值。**注意**：命中是"请求即响应"(同拍)，而 PerfReg 在同拍 req+rsp 时读到的是**上一次**请求的时间戳，故该值实际接近"两次取指的平均间隔"，不是纯取指延迟
- **取指命中率 / 缺失avg**：icache 的 `io.miss`、`io.missDone` 两个脉冲统计而来；`缺失avg` 即**平均缺失代价**，也就是文档 TMT（总缺失时间 = 缺失次数 × 缺失代价）里的那一项
- **LSU访存总周期**：内存读+写累计周期数（= rd total + wr total）
- **LSU mem rd/wr avg**：内存读/写平均延迟（cyc/access）
- **LSU dev avg**：外设访问平均延迟（串口/键盘/CLINT/VGA 等）
- **EXU calc**：计算类指令总执行周期（当前单周期，= 计算类指令数）
- **calc/mem/branch/jump/csr/sys%**：指令类别占比（decoder 统计）
- 不同 commit 的计数器含义可能不同（如早期无 PerfReg、604d59c 起才有命中率），以当时代码输出为准

### 519cf4f(五级流水线) 起的两点注意

- **指令类别百分比**：`519cf4f` 那行的类别计数还是按 `io.input.valid` 计的（属于该级的**占用拍数**，不是指令条数，百分比相对"各类别之和"算）；**从 `bbd3432` 起已改成按 `io.output.fire` 计数，恢复"指令条数占比"语义**（`Σ类别` ≈ 658280，比退休指令数略大，因为被重定向冲掉、但已经离开 IDU 的指令也计了一次）。
- **本版瓶颈不在流水线**：LSU 访存（rd 7.74M + wr 1.21M）+ icache 缺失（3.85M）≈ 12.80M / 13.71M = **93.4% 的周期在等访存**，所以 5 级流水线只比多周期版少 5.7% 周期（`bbd3432` 再降 4.5% 也只是把协议白等砍掉）。
- **取指次数 817065 vs 退休指令 581595**：约 29% 的取指被丢弃（重定向冲刷 + 提前取指），并且把 icache 缺失次数从 47.5K 顶到 70.9K（+49%）——错路径取指会真实地吃 miss 代价。
- 综合频率 `bbd3432` = 587.8 MHz（500MHz 目标下最差路径 slack 0.299ns，路径仍在 `ifu.icache.axi4Ctrler.io_readAddr`）。

### 92a825d 的取舍：拿 0.78% 周期换 12% 频率

- **做对了什么**：icache 的 `ar.valid/addr` 恢复成寄存器后，交给 Xbar 的是**寄存器信号**，一次切断了「icache 的 hit 锥 → Xbar 地址 mux / `isClint` 解码 → CLINT 的 `ar.fire` → `readCnt/readActive/dataFinish`」整族长组合锥 → 榜首从 CLINT 的 `readCnt`（1.085ns，其实是一条**不可敏化**的假路径：IFU 的取指地址永远不会落在 CLINT 的 `0x0200_0000` 段）换成真正的核内路径。
- **代价比预估略大**：每次 icache miss 的 AR 晚 1 拍（预期 +0.52%），实测 **+0.78%** —— 因为 AR 晚一拍也更容易在 Xbar 上把总线让给 LSU，`缺失avg` 从 54.31 涨到 **59.69 cyc/miss**；这部分常被流水线停顿吸收，所以总周期增幅（+0.78%）小于「miss 次数 × 5.4 拍」。
- **换来了什么**：频率 888 → **993.6 MHz**（+12%），面积 −232.5 µm²，而且**第一次看到了真实瓶颈** —— 不再是 cache/CLINT，而是
  - `exu.io_input_payload_rfReadData{1,2}_*`：IDU 的 **RF 读 + 三级前递 mux** → IDU→EXU 寄存器（0.951~0.957ns）
  - `ifu.state_0`：IFU 的次态逻辑（重定向 / 响应 / Done 的 mux，0.964ns）
- **判断**：如果只看周期，这 +0.78% 是净亏；但用新增的"真实时间"列算总账，`d1cdfe4` 的 15.25ms → `92a825d` 的 **13.91ms（赚 8.8%）** —— 频率涨得比周期亏得多。评分口径是周期 + 面积、频率只要求"500MHz 通过"，所以这 0.78% 周期在评分上仍是净亏；保留它的理由是频率余量（994MHz ≈ 2 倍）和"把假路径从报告里清掉、让真瓶颈暴露"。若只在乎评分，可以只回退 icache 那一处（CLINT 的寄存器化与计数器拆分应当保留）。

### c252c6c 的取舍：同步复位要花掉 0.36ns 关键路径（面积反而更小）

项目要求同步复位，改法只有一行（`Config.scala`）：

```scala
defaultConfigForClockDomains = ClockDomainConfig(
  resetKind = SYNC,            // SpinalHDL 默认是 ASYNC
  resetActiveLevel = HIGH)
```

- **验证方式（两个层面）**：生成 RTL 里 `or posedge reset` 从有到 **0 处**；网表里 `DFFR_X1`(579 个) + `DFFS_X1`(9 个) **全部消失**，只剩 `DFF_X1`(3036 个)。
- **功能验证**：`make perf` 的周期/指令数/全部 PERF 计数器与 `92a825d` **逐位相同** ✓ —— 复位只在上电生效，行为零变化。
- **对照实验**（只把 `resetKind` 改回 `ASYNC`，其他一个字不动）：

| 配置 | 面积 | 最差路径 | 频率 | 500MHz slack |
|---|---|---|---|---|
| `92a825d`（ASYNC，未清理复位）| 22,364.75 | 0.964ns | 993.6 MHz | +0.994ns |
| **c252c6c（SYNC + 清理）** | **22,478.33** | **1.387ns** | **698.6 MHz** | **+0.569ns ✓ 达标** |
| 对照（ASYNC + 同样的清理）| 22,625.43 | 1.029ns | 929.2 MHz | +0.924ns |

- **两条重要结论**：
  1. **同步复位的代价是"关键路径 +0.36ns"，而面积反而更小（−147 µm²）** —— 因为复位变成了"参与数据路径的高扇出信号"，每个带复位触发器 D 侧多一层 mux、复位还要像普通信号一样满足建立时间；而异步复位用专用复位脚、不需要 D 侧逻辑。**面积与关键路径是两本独立的账，减少线不保证缩短路径。**
  2. 同步复位**把一条本来不是最长的路径顶成了最长**：ASYNC 版榜首是 `ifu.rdataReg_31`（1.029ns），SYNC 版榜首变成 EXU 的 imm/branch/pcNext 锥（1.387ns）。
- **去掉可省的复位**（按"上电后可能被读而此前从未被写"的规则）：icache 的 `lineReg`(128b)/`wordCnt`/`wordSelReg`/`pcReg`/`indexReg`/`tagReg`、IFU 的 `pcOfReq`、LSU 的 `rdataReg`、CLINT 的 `readLen`/`readCnt`/`timeCountHighSnap`；**必须保留**的是各状态机、流水线 valid、AXI 握手 valid、icache 行有效位、CSR 的 `mstatus/mtvec/mcause`、CLINT 的 `timeCountLow/High`（项目要求初始为 0）。这一轮清理把同步复位的面积代价从 **+502 µm² 压到 +114 µm²**（相对 `92a825d`）。
- **注意**：报告里的"可达频率"会随"复位种类 + 再映射"大幅跳动（这一路走过 587→739→898→993→799→698 MHz，而期间周期数几乎没变），**判断标准应看 500MHz 目标下的 slack 是否为正**，不要只看这个数。
